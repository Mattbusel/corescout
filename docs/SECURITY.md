# Security

CoreScout is a program that watches what you do and can eventually change how
your machine runs. That deserves to be taken seriously, so this document is
about what it may do, what stops it, and where those stops actually live in the
code.

---

## The order the checks run in

```text
paused?                    →  Refused
outside its authority?     →  Refused        no autonomy mode overrides this
autonomy mode              →  Refused | NeedsApproval | continue
rate limit                 →  Refused | Allowed
```

Authority before autonomy is the load-bearing part. **Turning on Autopilot
must not be able to grant reach that Suggest did not have.** Autonomy decides
*whether a person is asked*; authority decides *what is on the table at all*.
There is a test named after that sentence.

All of it is `crates/permissions`, which touches nothing: no hardware access,
no processes, no files. It decides. Whatever carries a decision out lives
elsewhere, so a bug in the deciding can only ever be too strict or too
permissive on paper, and the enforcement point is one call that is easy to
find.

## Pause

One boolean, checked before anything else. There is no path through the
permission layer that acts while it is set, and the test that says so runs
against the most permissive configuration the product can be in.

Pausing does not stop observation or learning. It stops changes.

## What may be touched

Out of the box: CoreScout's own process, and nothing else. No folders, no
commands, no services, no network.

Everything else is granted explicitly, and some things cannot be granted at
all. The floor list is refused whatever a user asks for:

- `\Windows\System32`, `\Windows\SysWOW64`, `\Windows\WinSxS`
- registry hives and the system profile
- `.ssh`, `.aws`, `.gnupg`, Windows credential stores
- files named `id_rsa`, `id_ed25519`, `.env`, `.npmrc`, `credentials`, `ntuser.dat`

A person can grant CoreScout their project folder. They cannot grant it their
SSH key, even though it is inside that folder, because there is no operational
improvement that requires one and an accident that reaches it is
unrecoverable.

Containment is checked component by component, not by string prefix:
`C:\Projects\app` is **not** inside `C:\Projects\a`, and a prefix test says it
is. A path containing `..` anywhere is refused outright rather than resolved.

Nothing reaches the network. There is no allowed host by default and the
product has no reason to add one.

## What a capability may be

Capabilities are generated by CoreScout from observed agent activity, which
means the thing constructing them is a program reading untrusted input. They
are validated as if they came from a stranger:

- **No shell.** A step names a program and passes arguments as a vector.
  Nothing is handed to `cmd.exe` or `sh` to be re-parsed, so there is nowhere
  for a quoting mistake to become an execution.
- **No shell interpreters.** `cmd`, `powershell`, `pwsh`, `sh`, `bash`, `wsl`
  and friends are refused as programs. This is the rule that makes the others
  mean anything: `cmd /c "build && del *"` passes every other check, because
  the interesting half is inside a string none of them look at.
- **No metacharacters.** `& | ; > < \` $ ( ) *` in a command or argument is
  refused. They cannot do anything without a shell; their presence means the
  definition was built by splitting a shell command line, which is not how
  definitions are meant to be constructed.
- **A bare program name**, resolved on the path. Not an absolute path, which
  would let a generated definition name any executable on the machine; not a
  relative one, which would let it name something inside the repository being
  worked on.
- **No `..`** in any path or argument.
- **A verification step**, always. A capability that cannot check its own
  result can only ever report what it was told.
- **A timeout**, capped. A step that hangs is killed and reported as a failure
  with a reason, not waited on.
- **At most twelve steps.**

Boundaries are checked twice: once when the run is authorised, and again
immediately before each step starts. The second check is not redundant — a
definition can be edited while a run is in flight, and a capability that was
permitted must not become able to touch something new halfway through.

## Rate limits

A budget over a rolling window, not a cooldown between actions. A cooldown
permits an unbounded number of actions given enough time, which is exactly the
failure mode.

Twelve changes an hour, sixty a day, and a stop after three consecutive
failures. These are deliberately small: an operational improvement worth having
is not one that needs applying sixty times an hour, and a loop that wants to is
malfunctioning.

The failure streak becomes a question rather than a wall, because a person can
clear it and refusing outright would leave them with no way forward.

## The audit record

Every action produces an entry naming the action, its target, the reason, what
was expected, what actually happened, and when. `Event::action` takes all of
them, so an action logged without a reason does not compile, and
`is_accountable()` is what an audit export asserts before shipping.

The audit trail and the Activity timeline are one log. An audit trail that
lives apart from the timeline is one nobody reads, and a timeline that omits
the actions CoreScout took lies by omission.

## The local API

- Bound to `127.0.0.1` only. Nothing off the machine can reach it.
- Every route but `/health` requires a token from
  `%LOCALAPPDATA%\CoreScout\endpoint.json`, compared in full rather than
  short-circuiting on the first differing byte.
- Two routes, and neither serves a file. A path traversal has nothing to
  traverse to.
- Request bodies are capped on the `Content-Length` header, before anything is
  allocated.
- The desktop window never holds the token: it calls one command, and the shell
  process adds it. A page in that window has no way to learn the token even if
  something were injected into it.

## What CoreScout will not do

- Download and execute remote code. Nothing in this repository fetches
  anything at runtime.
- Escalate privilege. The installer is per-user and needs no administrator.
- Start at sign-in unless asked. Nothing writes that registry value on install,
  and when it is set it is a per-user `Run` entry, visible in Task Manager's
  Startup tab, removable there without CoreScout's cooperation.
- Transmit anything. No crate here opens an outbound connection.

## Reporting something

Open an issue at <https://github.com/mattbusel/corescout/issues>. If it is
sensitive, say so in the issue without the details and a contact will be
arranged. This is a small project and there is no bounty; there is a real
interest in getting this right.

## Known limits

- **The installers are unsigned.** SmartScreen will warn, and it should.
  Checksums are published beside every release and the source builds
  reproducibly enough to check.
- **Secret detection is a net, not a proof.** It catches known credential
  prefixes, secret-shaped flags and names, and high-entropy values, and is
  written to fail towards redacting too much. It cannot catch everything.
- **The endpoint file's permissions are the access control.** Anything that can
  read it can drive CoreScout — the same set of things that can read the
  database beside it. On Unix the mode is set explicitly; on Windows it relies
  on the inherited ACL of the user's local application data.
- **Nothing here defends against an administrator.** A process running as you
  can already do everything CoreScout can, by definition.
